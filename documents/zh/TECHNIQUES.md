# 游戏如何装进13KB

[🇺🇸 English](../../TECHNIQUES.md) | [🇰🇷 한국어](../ko/TECHNIQUES.md) | [🇯🇵 日本語](../ja/TECHNIQUES.md) | [🇨🇳 简体中文](TECHNIQUES.md)

Unicorn Prism Escape可装进一个**13,309字节的ZIP**。本文从游戏实际保存的内容开始，用简单语言解释当前实现。

## 1. 角色是图片文件吗

**是的，独角兽、恶魔和传送门都是普通图片文件。** 游戏以WebP格式加载它们。WebP是一种类似PNG的图片格式，可以用更少的字节保存同一幅图。

其他元素则直接用代码绘制：

| 看到的内容 | 制作方式 |
|---|---|
| 独角兽、恶魔、传送门 | 小型WebP图片 |
| 天空 | 颜色渐变 |
| 云 | 重叠的椭圆 |
| 棱镜 | 彩色几何图形 |
| 闪电和敌人的火焰 | 直线与曲线 |
| 光环和波动 | 半透明圆形 |

大型宣传封面是独立素材，不在游戏ZIP中。

### 让小图片依然好看

素材准备流程是：把较大的原画缩到游戏所需尺寸，简化颜色，再以这个小尺寸检查效果。

独角兽使用大图缩小后的**56×56**版本。缩小采用面积平均：一个输出像素综合它所覆盖的原图区域内的像素信息。

圆润的脸、小黑眼睛、彩虹鬃毛和清晰轮廓等重要特征通过少量颜色保持可辨识。一些边缘像素为半透明，在不引入大量颜色的情况下柔化边缘。角色图片使用完全透明、半透明、完全不透明三档透明度。

绘制时关闭自动图像平滑、对坐标取整并保持预定尺寸，避免再次模糊。独角兽为56×56，普通及远程恶魔为48×48，大型恶魔为96×96。

### WebP为什么能节省空间

当前WebP及对应PNG**解码后的像素完全相同**。这里WebP用更小的文件保存同一幅图。

| 图片 | PNG合计 | WebP合计 |
|---|---:|---:|
| 独角兽、恶魔、传送门 | 7,086字节 | 4,052字节 |

图片文件数据量约减少43%。这不是最终ZIP内的准确节省量，因为ZIP还会再次压缩。

多个姿势放在同一张称为**图集**的图片中，可以想象成一张小贴纸板。独角兽图集有五种姿势，通过复用和水平翻转表示八个移动方向。

图片位于`src/assets/`。仓库包含完成的PNG和WebP，而不是从概念原画重新生成全部素材的完整工具。

## 2. 静态图片怎么会有移动的腿

**图片文件始终不变，改变的是把图片局部画到屏幕上的位置。** 想象一个纸偶：身体固定，只移动腿部纸片。

### 第一步：从同一张图读取不同矩形

最简单的例子是48×48恶魔。绘制器把它当成三个矩形部分：

```text
一张静态图片，48×48
┌────────────────────────┐
│        身体和头         │ 上方36像素
├────────────┬───────────┤
│    左脚     │    右脚    │ 下方12像素
└────────────┴───────────┘
```

这不需要创建三个新文件。Canvas可以只复制已有图片中的一个矩形区域到屏幕上。

### 第二步：把各部分画在略有差异的位置

下表展示行走的基本思路，数值表示脚相对正常位置抬高多少：

| 时刻 | 身体 | 左脚 | 右脚 |
|---|---|---|---|
| A | 正常位置 | 0px | 0px |
| B | 正常位置 | 向上2px | 0px |
| C | 正常位置 | 0px | 0px |
| D | 正常位置 | 0px | 向上2px |
| 重复 | 正常位置 | 0px | 0px |

实际动画还经过中间位移。角色在地图上整体移动时，所有部分一起移动，再额外加上这些微小的腿部偏移。

### 第三步：每帧重画场景

游戏每帧重画背景和角色。旧脚的位置随着上一帧消失，再在新位置画脚。快速重复便产生走路的视觉效果。

Canvas的`drawImage()`可以同时指定**原图矩形**和**目标矩形**。下面的简化例子假设只有一张恶魔图片，不考虑它在实际图集中的偏移：

```js
// 参数：图片、原图x/y/宽/高、屏幕x/y/宽/高
// 身体复制到正常位置。
ctx.drawImage(image, 0, 0, 48, 36,
                    x, y, 48, 36);
// 左脚复制到比正常位置高2px的位置。
ctx.drawImage(image, 0, 36, 24, 12,
                    x, y + 36 - 2, 24, 12);
// 右脚复制到正常位置。
ctx.drawImage(image, 24, 36, 24, 12,
                    x + 24, y + 36, 24, 12);
```

只有目标位置改变，脚本身的像素不变。没有加载另一张行走图片，图中的关节也不是真的在弯曲。

### 第四步：用小公式决定偏移量

正弦波给出平滑来回变化的数值，再取整到完整像素，保持脚的清晰。一种符号抬左侧，另一种符号抬右侧。

这就是这里的**程序化动画**：用小规则生成动作，而不是为每一帧存储一张图。

普通及远程恶魔最多抬脚2px，大型恶魔最多6px。不同敌人使用不同时间偏移，避免整齐地同时迈步。紧贴脚部的阴影增加落地感。

### 独角兽原理相同，但切分更细

独角兽有正面、背面、侧面和斜向姿势，每种姿势需要不同切分位置。下部从56px图片的第43或45行开始。有些尾巴像素固定不动，不放入腿部切片。一些姿势的脚还会稍微左右移动。

腿部矩形必须排除需要固定的尾巴和身体轮廓，否则那些像素会跟着腿移动，像断开的碎片。按姿势设置切片范围和绘制顺序，让正确的部分连在一起。

独角兽的步态周期跟随**移动距离**：走得更远，周期推进更多；停止时腿也停止。腿部偏移最多2px。

这种方法成本低但有限制。在小尺寸下能有效表现走路，却不能像逐帧绘画或完整关节系统那样自由表现复杂膝盖弯曲。

**实现位置：** `src/systems/render-system.ts`中的`drawEnemy()`和`drawUnicorn()`。

## 3. 其他效果也复用简单元素

天空逐渐混合四种颜色。云由两层重叠椭圆构成，位置分散且漂移速度相同，避免不断改变重叠关系的云团。标题画面复用同一背景代码，但减少云的数量。

闪电是以不同线宽和颜色叠画的折线。敌人火焰使用多层曲线。波动则是半径增加、不透明度降低的圆。

冲锋效果在独角兽前方绘制三个淡化副本，用来传达独角攻击，并不额外给玩家设置冲刺速度。

Rainbow Wave把收集到的棱镜变为短暂存在的波动对象。它保留颜色，扩张0.6秒后消失。实际击退和清除敌弹会在300px范围内立即执行；扩散圆环是对此事件的视觉说明。

标题和结尾文字使用小型编码像素字母表，避免下载字体。

## 4. 没有音频文件，声音从何而来

**游戏保存的是制造声音的指令，而不是录音。** 浏览器的Web Audio API生成声音。

例如，指令可以是：

> 发出尖锐音调，快速降低音高，减小音量，然后停止。

只需少量数字就能描述，不必在MP3或WAV中保存大量录音采样。

### 共用的声音生成函数

`AudioSystem.tone()`接受起始音高、结束音高、时长、音量、开始时间和波形。波形是决定音色的重复形状：正弦波较柔和，方波和锯齿波较尖锐。

| 声音 | 基本思路 |
|---|---|
| 冲锋 | 上升的尖锐音，随后是下降的低音 |
| 闪电 | 极快的音高下降，加上低频冲击 |
| 敌人发射 | 两个短暂的下降扫频 |
| 波动 | 较长的下降音，加上棱镜收集音 |
| 收集和升级 | 一小串上升音符 |

音量渐入渐出，而不是突然开启和关闭。声音结束后断开音频节点。用户输入解锁音频，M将公共输出静音。

### 音乐是一份小乐谱

背景音乐把短旋律、音阶、和弦模式存成数字数组。低音、旋律、和弦和简单打击乐都使用同一生成函数。

随着关卡分组变化，增加音乐层次，并把速度从132提升到144、156、168 BPM。复用小乐谱即可产生变化，不用保存四段录音。

音量需要实际聆听。同一音量数值用于刺耳方波和柔和正弦波时，听感可能完全不同。自动检查能验证调度和清理，但不能判断混音是否悦耳。

**实现位置：** `src/systems/audio-system.ts`，重点是`tone()`、`music()`和`update()`。

## 5. 敌人如何追赶独角兽，又不挤成一团

### 先找到朝向玩家的方向

敌人不需要从图像中识别独角兽。游戏已经通过`World.positions`知道双方坐标。

用玩家位置减去敌人位置：

```text
敌人：   (100, 100)
独角兽： (400, 500)
差值：   (300, 400)
```

这表示应该向右下方移动。距离为500px，把差值除以500得到`(0.6, 0.8)`，这是长度为1的方向。这个步骤叫**归一化**。它把“往哪里”与“多快”分开，避免目标越远，敌人就自动越快。

再把方向乘以敌人速度。220px/s对应横向132px/s、纵向176px/s。以0.1秒为示例，就向右13.2px、向下17.6px。实际游戏每帧时间最多0.05秒。

```js
// 简化的直接追踪示例，尚未加上曲线与邻居分离。
const dx = player.x - enemy.x;
const dy = player.y - enemy.y;
const distance = Math.hypot(dx, dy) || 1;
velocity.x = dx / distance * speed;
velocity.y = dy / distance * speed;
```

AISystem计算速度，MovementSystem把它应用到位置。游玩中不断重复，敌人就能跟随玩家的新位置。目标是当前位置，不是对未来位置的预测。

### 给敌人略有不同的目标

如果所有敌人始终朝同一点前进，就会走相似的路线。因此游戏为每个敌人设置独角兽周围的小型移动目标：

```text
目标X = 独角兽X + cos(角度) × 偏移半径
目标Y = 独角兽Y + sin(角度) × 偏移半径
```

可以想象一个看不见的小点绕着独角兽转，敌人朝它前进。ID和游玩时间决定角度，让各敌人不必瞄准同一点。这个点只是目标，不会把敌人固定在完美圆周上。少量横向调整还会弯曲路线。

| 敌人 | 移动特征 |
|---|---|
| 近战 | 附近的移动目标，周期性切换到直接追赶 |
| 远程 | 较宽的移动目标和横向曲线，足够近时发射 |
| 大型 | 移动目标和周期性直接追赶，转向较缓 |

**进入120px范围后，所有类型都直接以独角兽为目标。** 额外偏移和曲线归零，但仍保留较弱的邻居分离力。“直接追赶”改变的是转向方式，不是提高速度设置。

地图没有挡路的墙，因此使用方向计算，而非A*这类迷宫寻路算法。远程敌人发射时也瞄准独角兽当时的位置，子弹发出后不会继续转弯追踪。

### 与邻居保持距离

每个敌人合并两个意图：

1. 向玩家靠近。
2. 另一个敌人太近时，远离它。

就像一群人朝同一扇门走，同时给彼此留一点空间。游戏把这些方向相加，决定最终移动。

当移动方向几乎互相抵消时，代码让剩余方向保持很小，不把它放大回全速，以免产生不稳定运动。直接追赶时分离力也较弱，使敌人仍能接近玩家。

这会**减少重叠，但不禁止重叠**。敌人之间没有硬墙，碰撞圆也小于角色图像。代码直接比较所有敌人对，在最多35个存活敌人的规模下可以处理。更大的群体需要更高效的邻居搜索。

**实现位置：** `src/systems/ai-system.ts`中的`AISystem.update()`。

## 6. 十个关卡如何构成

十个关卡复用同一大场地，只改变少量数据：

- 七个棱镜的位置。
- 初始敌人数及可出现类型。
- 敌人和子弹的速度加成。
- 增援频率及最大数量。
- 天空配色与音乐分组。

前期棱镜离起点较近，后期路线遍布全场。远程敌人从第4关出现，大型从第7关出现。传送门一开始就存在，集齐七色前呈灰色。

增援从地图边缘增加**随机的一种可出现敌人，共一只**。间隔为第1~2关10秒、第3~5关5秒、第6~8关4秒、第9~10关3秒。新敌人从不同方向施压，而不只是加入玩家身后的队伍。

### 敌人变强不代表关卡一定更难

玩家也会获得地图信息、速度、自动闪电和其他能力。这些优势可以叠加，所以更快的敌人本身不能保证更高难度。

难度由路程、初始数量、增援、速度、升级时机共同决定。三行升级按顺序解锁，完整一局最终获得全部九项，因此关键是**先获得哪些**。

目标时长约为**五分钟**。本地面板比较路线和升级顺序，但时间来自距离、速度、绕路余量的估算，并非真人实测。判断难度仍需要实际游玩。

重试的游玩时间计入最终关卡记录，升级和失败画面的等待时间不计入。

**实现位置：** `src/game.ts`中的`STAGES`、`ENEMIES`，以及`src/systems/rules-system.ts`。本地面板由`tools/build-dashboard.mjs`生成。

## 7. 所有内容如何装进一个小ZIP

源码项目远大于提交文件，构建只保留游戏需要的部分：

1. 把TypeScript模块合并为JavaScript。
2. 删除开发专用代码，缩短内部名称。
3. 使用Roadroller进一步打包JavaScript。
4. 把代码、样式和WebP数据嵌入一个index.html。
5. 使用Zopfli将HTML压缩为ZIP。

因此ZIP只有**一个HTML文件**，但它仍包含真实图片数据。图片并没有变成手写的绘图代码。

文档、本地面板、原始PNG副本和宣传图不在提交包内。

修改后必须测量实际ZIP。代码更短不一定压缩得更小。接近限制时，调整音量数字也可能影响大小。预留空间能容纳这类变化。

## 8. 核心要点

- 需要清楚辨识的形象保存成小图片，简单效果用代码绘制。
- 静态图片的各部分画在不同位置，也能呈现运动。
- 复用小型声音生成器和乐谱，不保存录音。
- 敌人的压力取决于出现地点和时间，不仅是数量。
- 以游戏尺寸看图、用耳朵听声音、实际游玩判断难度。
- 测量ZIP，不猜测修改成本。

Node检查可以验证数据和时间处理。视觉质量、触屏操作、音量平衡、难度也需要真实浏览器测试和聆听。
