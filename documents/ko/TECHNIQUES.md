# 게임이 13KB 안에 들어가는 원리

[🇺🇸 English](../../TECHNIQUES.md) | [🇰🇷 한국어](TECHNIQUES.md) | [🇯🇵 日本語](../ja/TECHNIQUES.md) | [🇨🇳 简体中文](../zh/TECHNIQUES.md)

Unicorn Prism Escape는 **13,309바이트 ZIP** 안에 들어간다. 이 문서는 현재 게임에 무엇을 저장하고 어떻게 사용하는지 쉽게 설명한다.

## 1. 캐릭터는 이미지 파일인가?

**맞다. 유니콘·악마·게이트는 일반적인 이미지 파일이다.** WebP라는 형식으로 저장한다. WebP는 PNG처럼 이미지를 저장하는 형식이며, 같은 그림을 더 작은 파일로 담을 수 있다.

다른 요소는 코드로 직접 그린다.

| 화면에 보이는 것 | 만드는 방식 |
|---|---|
| 유니콘, 악마, 게이트 | 작은 WebP 이미지 |
| 하늘 | 색상 그라데이션 |
| 구름 | 여러 타원을 겹쳐 그리기 |
| 프리즘 | 색이 있는 도형 |
| 번개, 적 불꽃 | 선과 곡선 |
| 오라, 파동 | 반투명 원 |

큰 홍보용 커버 이미지는 별개다. 게임 ZIP 안에 들어 있지 않다.

### 작은 이미지를 보기 좋게 만들기

이미지 준비는 큰 원화를 게임에 표시할 크기로 축소하고, 색상을 정리한 다음 그 작은 크기에서 확인하는 순서다.

유니콘은 큰 원화를 줄인 **56×56 이미지**를 사용한다. 축소에는 면적 평균을 쓴다. 출력 픽셀 하나가 담당하는 원본 영역의 픽셀 정보를 합치는 방식이다.

통통한 얼굴, 작은 검은 눈, 무지개 갈기와 명확한 윤곽을 유지하면서 색상 수를 제한한다. 가장자리 일부 픽셀은 반투명하다. 많은 색상을 추가하지 않고도 경계가 조금 부드럽게 보이도록 한다. 캐릭터에는 완전 투명·반투명·완전 불투명의 세 단계가 있다.

이후 렌더러에서는 자동 이미지 보간을 끄고 좌표를 반올림하며 의도한 크기로 출력해 다시 흐려지는 것을 줄인다. 유니콘은 56×56, 일반·원거리 악마는 48×48, 대형 악마는 96×96이다.

### WebP로 용량을 줄이는 원리

현재 WebP와 대응하는 PNG를 열어 복원한 픽셀은 **완전히 같다**. 이 경우 그림을 바꾸지 않고 파일 크기만 줄인 것이다.

| 이미지 | PNG 합계 | WebP 합계 |
|---|---:|---:|
| 유니콘·악마·게이트 | 7,086바이트 | 4,052바이트 |

이미지 파일 기준 약 43% 감소다. ZIP은 다시 압축하므로 최종 ZIP 안에서 정확히 그만큼 줄었다는 의미는 아니다.

여러 포즈는 **아틀라스**라는 한 이미지에 모아 저장한다. 작은 스티커판처럼 생각하면 된다. 유니콘은 5개 포즈를 저장하고 좌우 반전으로 재사용해 8방향을 표현한다.

이미지는 `src/assets/`에 있다. 저장소에는 완성된 PNG와 WebP가 있으며, 큰 원화부터 결과물을 모두 재생성하는 제작 도구가 들어 있는 것은 아니다.

## 2. 정지 이미지인데 어떻게 다리가 움직이는가?

**이미지 파일은 바뀌지 않는다. 이미지의 일부를 화면에 그리는 위치만 바뀐다.** 몸통은 가만히 두고 다리 조각을 움직이는 종이 인형을 생각하면 된다.

### 1단계: 같은 이미지에서 서로 다른 사각형 영역을 읽는다

가장 단순한 예시는 48×48 악마다. 렌더러는 이를 사각형 세 조각처럼 다룬다.

```text
정지 이미지 한 장, 48×48
┌────────────────────────┐
│                        │
│       몸통 + 머리       │  위쪽 36픽셀
│                        │
├────────────┬───────────┤
│ 왼쪽 발 영역│ 오른쪽 발 │  아래쪽 12픽셀
└────────────┴───────────┘
```

파일을 세 개로 만드는 것이 아니다. Canvas는 기존 이미지에서 원하는 사각형 부분만 복사해 화면에 그릴 수 있다.

### 2단계: 각 조각을 조금 다른 위치에 그린다

다음 표는 걷는 모습을 만드는 기본 원리다. 숫자는 평소 위치보다 발을 얼마나 위로 그리는지 뜻한다.

| 순간 | 몸통 | 왼발 | 오른발 |
|---|---|---|---|
| A | 원래 위치 | 0px | 0px |
| B | 원래 위치 | 위로 2px | 0px |
| C | 원래 위치 | 0px | 0px |
| D | 원래 위치 | 0px | 위로 2px |
| 반복 | 원래 위치 | 0px | 0px |

실제 움직임에는 중간 이동량도 들어간다. 캐릭터가 맵을 이동할 때는 세 조각이 모두 함께 이동하며, 그 위치에 발의 작은 움직임을 추가한다.

### 3단계: 매 프레임 화면을 다시 그린다

게임은 프레임마다 배경과 캐릭터를 다시 그린다. 이전 발 위치는 이전 화면과 함께 사라지고 새 위치에 발을 그린다. 이것을 빠르게 반복하면 발이 움직이는 것처럼 보인다.

Canvas의 `drawImage()`에는 **원본에서 가져올 영역**과 **화면에 그릴 영역**을 따로 지정하는 형태가 있다. 아래는 원리를 위한 단순한 예시다. 실제 아틀라스 내부 좌표 대신 악마 한 장만 있다고 가정한다.

```js
// 이미지, 원본 x/y/너비/높이, 화면 x/y/너비/높이

// 몸통은 원래 자리에 그린다.
ctx.drawImage(image, 0, 0, 48, 36,
                    x, y, 48, 36);

// 왼발 부분만 복사해 원래 위치보다 2px 위에 그린다.
ctx.drawImage(image, 0, 36, 24, 12,
                    x, y + 36 - 2, 24, 12);

// 오른발은 원래 자리에 그린다.
ctx.drawImage(image, 24, 36, 24, 12,
                    x + 24, y + 36, 24, 12);
```

바뀌는 것은 그리는 목적지다. 발 그림의 픽셀은 그대로다. 다른 보행 이미지를 불러오는 것도 아니고 이미지 속 무릎이 실제로 구부러지는 것도 아니다.

### 4단계: 작은 수식으로 움직일 양을 정한다

사인파는 값이 부드럽게 오르내리게 한다. 발이 선명하도록 값을 정수 픽셀로 반올림한다. 한쪽 부호일 때 왼쪽 발을, 반대일 때 오른쪽 발을 들어 올린다.

이 게임에서 **procedural animation, 즉 절차적 애니메이션**은 이런 의미다. 각 프레임의 그림을 전부 저장하는 대신 작은 규칙으로 움직임을 계산한다.

일반·원거리 악마는 최대 2px, 대형 악마는 최대 6px 발을 든다. 개체마다 시간 차이를 줘 전부 같은 순간에 걷지 않게 한다. 발 가까이에 그림자를 두면 땅에 붙어 있는 느낌도 난다.

### 유니콘도 같은 원리지만 자르는 위치가 더 복잡하다

유니콘에는 정면·후면·측면·대각선 포즈가 있다. 포즈마다 다리가 있는 위치가 달라 따로 잘라야 한다. 56px 이미지의 43행 또는 45행부터 아래 영역을 나누고, 꼬리 일부는 다리 조각에 넣지 않고 고정한다. 일부 포즈의 발은 좌우로도 조금 움직인다.

다리 사각형에는 고정되어야 하는 꼬리나 몸통 윤곽선을 넣지 않아야 한다. 그런 픽셀이 들어가면 다리와 함께 움직여 분리된 조각처럼 보일 수 있다. 포즈별로 자르는 영역과 그리는 순서를 정해 알맞은 부분끼리 붙어 있게 한다.

유니콘 보행 주기는 **실제로 이동한 거리**에 연결된다. 많이 이동하면 발 움직임도 더 진행되고, 멈추면 발도 멈춘다. 발 이동량은 최대 2px이다.

이 방식은 저렴하지만 한계도 있다. 작은 캐릭터가 걷는 느낌을 주기에는 좋지만, 복잡한 무릎 움직임은 프레임별 그림이나 관절 시스템만큼 잘 표현할 수 없다.

**실제 코드:** `src/systems/render-system.ts`의 `drawEnemy()`, `drawUnicorn()`.

## 3. 다른 효과도 단순한 재료를 재사용한다

하늘은 네 색상을 서서히 섞는다. 구름은 타원 몇 개를 두 겹으로 그린다. 위치를 띄우고 같은 속도로 이동시켜 시간이 지날수록 마구 겹치는 것을 피한다. 타이틀은 같은 배경 코드를 쓰되 구름 수를 줄인다.

번개는 꺾인 선을 굵기와 색상을 바꾸며 겹쳐 그린다. 적 불꽃은 곡선 도형을 겹친다. 파동은 원의 반경을 키우면서 투명하게 만든다.

돌격 표현은 유니콘 복사본 세 개를 앞쪽에 반투명하게 그린다. 뿔 공격을 보여주는 효과이며 별도의 돌진 속도를 플레이어에게 추가하는 것은 아니다.

Rainbow Wave는 수집한 프리즘을 잠깐 유지되는 파동 객체로 바꾼다. 프리즘 색을 유지하고 0.6초 동안 퍼지다 사라진다. 실제 적 밀어내기와 탄환 제거는 300px 안에 즉시 적용하며, 퍼지는 링은 그 사건을 보여주는 표현이다.

타이틀·엔딩 글씨도 외부 폰트를 다운로드하지 않고 작은 픽셀 글자 데이터를 사용한다.

## 4. 오디오 파일 없이 어떻게 소리를 만드는가?

**소리 녹음 대신 소리를 만드는 지시를 저장한다.** 브라우저의 Web Audio API가 실제 소리를 생성한다.

예를 들면 이런 지시다.

> 날카로운 소리를 내고, 음높이를 빠르게 내린 뒤, 음량을 줄여 멈춘다.

몇 개의 숫자로 표현할 수 있으므로 MP3·WAV에 녹음된 많은 샘플을 저장할 필요가 없다.

### 공통 소리 생성 함수

`AudioSystem.tone()`은 시작 음높이, 끝 음높이, 길이, 음량, 시작 시간, 파형을 받는다. 파형은 소리의 기본 성격을 만드는 반복 모양이다. 사인파는 부드럽고 사각파·톱니파는 거칠다.

| 소리 | 기본 구성 |
|---|---|
| 돌격 | 날카롭게 올라가는 음 + 뒤따르는 낮아지는 음 |
| 번개 | 매우 빠른 음높이 하강 + 낮은 타격음 |
| 적 발사 | 짧게 내려가는 음 두 개 |
| 파동 | 조금 길게 내려가는 음 + 프리즘 수집음 |
| 수집·강화 | 짧게 올라가는 음표들 |

음량을 갑자기 켜고 끄지 않고 서서히 올리고 내린다. 재생이 끝나면 오디오 노드 연결을 해제한다. 사용자 입력 이후 소리를 활성화하고 M으로 공통 출력을 음소거한다.

### 배경음은 작은 악보다

멜로디, 음계, 화음 진행을 작은 숫자 배열로 저장한다. 같은 소리 함수를 베이스·멜로디·화음·간단한 타악기에 재사용한다.

스테이지 구간이 바뀌면 음표를 추가하고 템포를 132→144→156→168 BPM으로 높인다. 녹음 네 개를 넣는 대신 작은 악보를 재사용해 변화를 만든다.

음량은 직접 들어봐야 한다. 같은 수치라도 날카로운 사각파와 부드러운 사인파의 체감 크기는 다르다. 자동 검사는 재생 예약과 정리를 확인하지만 듣기 좋은 밸런스인지는 판단하지 못한다.

**실제 코드:** `src/systems/audio-system.ts`의 `tone()`, `music()`, `update()`.

## 5. 적은 어떻게 유니콘을 쫓으면서 뭉치지 않는가?

### 먼저 플레이어가 있는 방향을 계산한다

적이 화면 속 그림을 보고 유니콘을 알아보는 것은 아니다. 게임은 `World.positions`에서 두 대상의 좌표를 이미 알고 있다.

플레이어 위치에서 적 위치를 빼면 된다.

```text
적:       (100, 100)
유니콘:   (400, 500)
좌표 차이: (300, 400)
```

이 차이는 오른쪽과 아래쪽으로 이동해야 한다는 뜻이다. 두 대상의 거리는 500px이다. 차이를 500으로 나누면 `(0.6, 0.8)`이라는 길이 1의 방향이 나온다. 이것을 **정규화**라고 한다. “어디로?”와 “얼마나 빠르게?”를 분리해 멀리 있는 플레이어를 향한다고 적이 자동으로 빨라지지 않게 한다.

이 방향에 적의 속도를 곱한다. 속도가 초당 220px이면 가로 초당 132px, 세로 초당 176px가 된다. 예시로 0.1초 동안이라면 오른쪽으로 13.2px, 아래로 17.6px 이동한다. 실제 게임의 한 프레임 시간은 최대 0.05초로 제한된다.

```js
// 곡선 이동과 적끼리의 간격 처리를 빼고 설명한 직접 추적 예시
const dx = player.x - enemy.x;
const dy = player.y - enemy.y;
const distance = Math.hypot(dx, dy) || 1;

velocity.x = dx / distance * speed;
velocity.y = dy / distance * speed;
```

AISystem이 속도를 계산하고 MovementSystem이 그 속도로 위치를 바꾼다. 플레이 중에 반복하므로 플레이어가 방향을 바꾸면 적도 새 위치를 따라간다. 플레이어의 미래 위치를 예측하는 것이 아니라 현재 위치를 기준으로 한다.

### 적마다 조금 다른 곳을 목표로 삼는다

모든 적이 항상 정확히 같은 점을 향하면 비슷한 길로 모이게 된다. 그래서 각 적에게 유니콘 주변의 작은 움직이는 목표점을 준다.

```text
목표 X = 유니콘 X + cos(각도) × 목표점 반경
목표 Y = 유니콘 Y + sin(각도) × 목표점 반경
```

유니콘 주위를 도는 보이지 않는 점이 있다고 생각하면 된다. 적은 그 점을 향한다. ID와 플레이 시간이 각도를 정하므로 모든 적이 같은 점을 향하지 않는다. 이 점은 목표일 뿐, 적을 완벽한 원 위에 묶어 두지는 않는다. 옆 방향 성분을 조금 더해 이동 경로도 휘게 한다.

| 적 | 이동 특성 |
|---|---|
| 근거리 | 가까운 이동 목표점을 향하다 주기적으로 직접 추적 |
| 원거리 | 더 넓은 이동 목표점과 옆으로 휘는 움직임, 가까워지면 발사 |
| 대형 | 이동 목표점과 주기적 직접 추적, 서서히 방향 전환 |

**120px 안에 들어오면 모든 종류가 유니콘을 직접 목표로 삼는다.** 목표점 오프셋과 추가 곡선 성분은 0이 되지만, 다른 적과 간격을 벌리는 약한 힘은 남는다. 여기서 “직접 추적”은 조향 방식의 변화이며 속도 설정이 올라간다는 뜻은 아니다.

맵에 길을 막는 벽이 없으므로 A* 같은 미로 길찾기 대신 방향 계산을 사용한다. 원거리 적도 발사 순간 유니콘 위치를 조준하며, 탄환이 발사 후 계속 유니콘을 향해 방향을 바꾸지는 않는다.

### 이웃한 적과 간격을 둔다

각 적은 두 가지 방향을 함께 고려한다.

1. 플레이어에게 다가간다.
2. 다른 적이 너무 가까우면 그 적에게서 멀어진다.

같은 문으로 걸어가면서 서로 약간의 간격을 두는 사람들과 비슷하다. 두 방향을 더해 최종 이동 방향을 정한다.

여러 이동 방향이 거의 상쇄되면 남은 작은 방향을 최대 속도로 증폭하지 않고 작게 유지한다. 불안정한 움직임을 줄이기 위해서다. 직접 추적 중에는 서로 밀어내는 힘도 낮춰 플레이어에게 접근할 수 있게 한다.

이는 **겹침을 줄이는 방법이지 겹침 금지는 아니다.** 적 사이에 단단한 벽이 있는 것이 아니며 충돌 원은 그림보다 작다. 모든 적 쌍을 비교하지만 최대 35마리 규모라 감당할 수 있다. 훨씬 많은 적을 쓰려면 가까운 이웃을 효율적으로 찾는 방법이 필요하다.

**실제 코드:** `src/systems/ai-system.ts`의 `AISystem.update()`.

## 6. 10개 스테이지는 어떻게 구성되는가?

10개 스테이지는 큰 맵 하나를 재사용하고 작은 데이터만 바꾼다.

- 프리즘 7개의 위치
- 초기 적 수와 등장 가능한 종류
- 적·탄환의 추가 속도
- 증원 간격과 최대 개체 수
- 하늘 색상과 음악 구간

초반 프리즘은 시작점에 가깝고 후반은 맵 전체에 퍼진다. 원거리 적은 4스테이지, 대형은 7스테이지부터 나온다. 게이트는 처음부터 회색으로 있고 7색을 모으면 열린다.

증원은 가장자리에서 **등장 가능한 적 중 무작위 한 마리**를 추가한다. 1~2스테이지 10초, 3~5는 5초, 6~8은 4초, 9~10은 3초 간격이다. 이미 플레이어 뒤에 모여 있는 적만 피하는 상황에 새로운 방향의 압박을 만든다.

### 적이 강해진다고 스테이지도 무조건 어려워지는 것은 아니다

플레이어도 지도 정보, 이동 속도, 자동 번개와 여러 능력을 얻는다. 이 장점들이 합쳐지므로 적이 빨라진다는 사실만으로 난이도 상승을 보장할 수는 없다.

난이도에는 이동 거리·초기 적 수·증원·속도·강화 시점이 함께 영향을 준다. 세 강화 행은 순서대로 해금된다. 완주 과정에서 9개를 모두 얻게 되므로 핵심은 **무엇을 먼저 얻느냐**다.

목표는 **약 5분**이다. 로컬 대시보드는 경로와 강화 순서를 비교하지만 시간은 거리·속도·우회 가정에 따른 추정치다. 실제 사람의 완주 기록이 아니다. 난이도 판단에는 실제 플레이가 필요하다.

재도전에 쓴 시간은 기록에 포함하고 강화·실패 화면에서 기다린 시간은 제외한다.

**실제 코드:** `src/game.ts`의 `STAGES`, `ENEMIES`와 `src/systems/rules-system.ts`. 대시보드는 `tools/build-dashboard.mjs`로 만든다.

## 7. 어떻게 작은 ZIP 하나에 담는가?

개발 저장소는 제출물보다 훨씬 크다. 빌드에서는 게임에 필요한 것만 남긴다.

1. TypeScript 모듈을 JavaScript로 합친다.
2. 개발 전용 코드를 빼고 내부 이름을 줄인다.
3. Roadroller로 JavaScript를 더 작게 포장한다.
4. 코드·스타일·WebP 이미지 데이터를 `index.html` 하나에 넣는다.
5. Zopfli로 HTML을 압축해 ZIP을 만든다.

그래서 ZIP에는 **HTML 하나만 있지만 그 안에는 실제 이미지 데이터가 들어 있다.** 이미지가 손으로 그리는 코드로 변한 것은 아니다.

문서·로컬 대시보드·원본 PNG·홍보 이미지는 제출물 밖에 남는다.

변경 후에는 실제 ZIP을 측정해야 한다. 코드가 짧아졌다고 압축 결과도 무조건 작아지는 것은 아니다. 한계에 가까워지면 효과음 음량 숫자 변경도 용량에 영향을 줄 수 있다. 여유 공간은 이런 변경을 수용하는 데 필요하다.

## 8. 핵심 원리

- 식별이 중요한 캐릭터는 작은 이미지로, 단순한 효과는 코드로 만든다.
- 정지 이미지도 부분별로 다른 위치에 다시 그리면 움직여 보인다.
- 녹음 파일 대신 소리 생성 함수와 작은 악보를 재사용한다.
- 적의 압박은 개체 수뿐 아니라 등장 위치와 시점에도 달려 있다.
- 그림은 실제 크기로 보고, 소리는 듣고, 난이도는 플레이해 판단한다.
- 용량은 예상하지 말고 ZIP으로 측정한다.

Node 검사는 게임 데이터와 시간 처리를 확인한다. 그림의 품질, 터치 조작, 음량 밸런스와 난이도는 실제 브라우저 확인과 청음도 필요하다.

코드 구조는 [ARCHITECTURE.md](ARCHITECTURE.md)에서 설명한다.
