# ゲームを13KBに収める仕組み

[🇺🇸 English](../../TECHNIQUES.md) | [🇰🇷 한국어](../ko/TECHNIQUES.md) | [🇯🇵 日本語](TECHNIQUES.md) | [🇨🇳 简体中文](../zh/TECHNIQUES.md)

Unicorn Prism Escapeは**13,309バイトのZIP**に収まります。この文書は、実際に何を保存しているかから始め、現在の実装をやさしく説明します。

## 1. キャラクターは画像ファイルなのか

**はい。ユニコーン、悪魔、ゲートは普通の画像ファイルです。** WebPとして読み込みます。WebPはPNGのような画像形式で、同じ絵をより少ないバイト数で保存できます。

それ以外のものはコードで直接描きます。

| 見えるもの | 作り方 |
|---|---|
| ユニコーン、悪魔、ゲート | 小さなWebP画像 |
| 空 | 色のグラデーション |
| 雲 | 重ねた楕円 |
| プリズム | 色付きの図形 |
| 雷と敵の炎 | 線と曲線 |
| オーラと波動 | 半透明の円 |

宣伝用の大きなカバー画像は別物で、ゲームZIPには含まれません。

### 小さな画像を見やすくする

画像の準備は、大きい原画をゲームの表示サイズに縮小し、色を整理し、その小さいサイズで確認する流れです。

ユニコーンは大きな絵を縮小した**56×56**画像です。縮小には面積平均を使います。出力の1ピクセルが担当する原画の領域の情報をまとめる方法です。

ふっくらした顔、小さな暗い目、虹のたてがみ、明確な輪郭を少数の色で保ちます。端の一部は半透明にして、多くの色を増やさずに輪郭を柔らかくします。キャラクターの透明度は、完全透明・半透明・不透明の3段階です。

描画では自動画像補間を切り、座標を丸め、意図した大きさを保って再びぼやけるのを防ぎます。ユニコーンは56×56、通常・遠距離悪魔は48×48、大型悪魔は96×96です。

### WebPで容量が減る理由

現在のWebPと対応するPNGは、**復元したピクセルが完全に同じ**です。同じ絵を小さなファイルで保存しています。

| 画像 | PNG合計 | WebP合計 |
|---|---:|---:|
| ユニコーン、悪魔、ゲート | 7,086バイト | 4,052バイト |

画像ファイルのデータ量で約43%減です。ZIPで再圧縮するため、最終ZIP内の節約量そのものではありません。

複数のポーズは**アトラス**という1枚の画像にまとめます。小さなシールの台紙のようなものです。ユニコーンは5ポーズを再利用・左右反転し、8方向を表現します。

画像は`src/assets/`にあります。完成したPNGとWebPはありますが、原画からすべてを再生成する制作ツールが入っているわけではありません。

## 2. 静止画なのに、なぜ脚が動くのか

**画像ファイルは変わりません。画像の一部を描く場所が変わります。** 胴体を固定して脚の部品を動かす紙人形を想像してください。

### 1段階目：同じ画像から別々の長方形を読む

単純な例は48×48の悪魔です。描画時には3つの長方形の部品として扱います。

```text
静止画像1枚、48×48
┌────────────────────────┐
│        胴体と頭         │ 上36ピクセル
├────────────┬───────────┤
│   左の足    │   右の足   │ 下12ピクセル
└────────────┴───────────┘
```

3つの新しいファイルを作るのではありません。Canvasは既存画像の長方形部分だけを画面へコピーできます。

### 2段階目：部品を少し違う位置に描く

次の数値は、通常位置から足をどれだけ持ち上げるかです。

| 瞬間 | 胴体 | 左足 | 右足 |
|---|---|---|---|
| A | 通常位置 | 0px | 0px |
| B | 通常位置 | 上へ2px | 0px |
| C | 通常位置 | 0px | 0px |
| D | 通常位置 | 0px | 上へ2px |
| 繰り返し | 通常位置 | 0px | 0px |

実際には中間の移動量も使います。キャラクター全体がマップを移動する位置に、この小さな足の動きを足します。

### 3段階目：フレームごとに描き直す

毎フレーム背景とキャラクターを描き直します。前の足の位置は前の画面とともに消え、新しい位置に足を描きます。高速に繰り返すと歩いて見えます。

Canvasの`drawImage()`は**画像内の読み取り領域**と**画面上の描画領域**を別々に指定できます。以下はアトラス内のオフセットを省き、悪魔1枚だけを使う説明用の例です。

```js
// 画像、元画像のx/y/幅/高さ、画面のx/y/幅/高さ
// 胴体は通常位置へ。
ctx.drawImage(image, 0, 0, 48, 36,
                    x, y, 48, 36);
// 左足だけ通常位置より2px上へ。
ctx.drawImage(image, 0, 36, 24, 12,
                    x, y + 36 - 2, 24, 12);
// 右足は通常位置へ。
ctx.drawImage(image, 24, 36, 24, 12,
                    x + 24, y + 36, 24, 12);
```

変わるのは描画先だけです。足のピクセルは同じです。別の歩行画像を読み込まず、画像の膝が実際に曲がるわけでもありません。

### 4段階目：小さな式で移動量を選ぶ

サイン波で滑らかに増減する値を作り、整数ピクセルに丸めて足を鮮明にします。一方の符号で左側、反対で右側を持ち上げます。

ここでいう**プロシージャルアニメーション**とは、各フレームの画像を保存せず、小さな規則で動きを作ることです。

通常・遠距離悪魔は最大2px、大型悪魔は最大6px足を上げます。敵ごとにタイミングをずらし、一斉に同じ足を出さないようにします。足の近くの影は接地感を作ります。

### ユニコーンも同じ仕組みだが、切り方が細かい

正面、背面、側面、斜めのポーズは脚の位置が違うため、切り出す位置も変えます。56px画像の43行目または45行目から下を分割し、尻尾の一部は脚に含めず固定します。ポーズによって足を横にも少し動かします。

固定すべき尻尾や胴体の輪郭を脚の長方形に含めると、一緒に動いて切り離されたように見えます。ポーズ別の切り出し領域と描画順で、正しい部品同士をつなげます。

ユニコーンの周期は**移動距離**に対応します。遠く歩くほど脚の周期が進み、止まると脚も止まります。足の移動量は最大2pxです。

安価な方法ですが限界もあります。小さい絵に歩行感を与えるには十分でも、複雑な膝の曲げ方は個別に描いたフレームや関節システムほど自由に表現できません。

**実装：** `src/systems/render-system.ts`の`drawEnemy()`と`drawUnicorn()`。

## 3. 他の効果も単純な材料を再利用する

空は4色を徐々に混ぜます。雲は楕円を2層に重ね、位置を離して同じ速さで流します。これで重なり方が常に大きく変わる密集を避けます。タイトルは同じ背景コードで雲を減らします。

雷はギザギザの線を太さと色を変えて重ね、敵の炎は曲線を重ねます。波動は円の半径を増やしながら不透明度を下げます。

突進の見た目はユニコーンの薄いコピーを前方に3つ描いて作ります。角攻撃を示す効果であり、プレイヤーに別のダッシュ速度を加えるものではありません。

Rainbow Waveでは収集したプリズムを短命な波動に変えます。色を保持し、0.6秒広がって消えます。敵の押し戻しと敵弾消去は300px以内に即時適用され、広がる円はその出来事を説明する見た目です。

タイトル・エンディング文字は小さな符号化済みピクセル文字データで、フォントのダウンロードを避けます。

## 4. 音声ファイルなしで音を作る仕組み

**音の録音ではなく、音を作る指示を保存します。** ブラウザーのWeb Audio APIが音声を生成します。

例えば、指示は次のようになります。

> 鋭い音を出し、音程を急に下げ、音量を減らして止める。

少数の数値で表せるので、MP3やWAVのような大量の録音サンプルを保存する必要がありません。

### 共通の音生成関数

`AudioSystem.tone()`は開始音程、終了音程、長さ、音量、開始時刻、波形を受け取ります。波形は音の基本的な性格を決める反復形状です。サイン波は滑らかで、矩形波とのこぎり波は鋭い音になります。

| 音 | 基本構成 |
|---|---|
| 突進 | 上昇する鋭い音と、続く下降する低音 |
| 雷 | 急激な音程下降と低い衝撃音 |
| 敵の発射 | 短い下降音を2つ |
| 波動 | 長めの下降音とプリズム収集音 |
| 収集・強化 | 短く上昇する音列 |

急にオン・オフせず、音量を上げ下げします。終了した音声ノードは接続を解除します。ユーザー入力で音声を有効にし、Mで共通出力をミュートします。

### 音楽は小さな楽譜

短い旋律、音階、和音パターンを数値配列に保存します。同じ音生成関数でベース、旋律、和音、簡単な打楽器を鳴らします。

ステージ区間に応じて音を増やし、テンポを132→144→156→168 BPMへ上げます。4つの録音を保存せず、小さい楽譜を再利用して変化を作ります。

音量は実際に聴く必要があります。同じ数値でも鋭い矩形波と柔らかいサイン波は違って聞こえます。自動検査は再生予約や後片付けを確認できますが、心地よいバランスかは判断できません。

**実装：** `src/systems/audio-system.ts`の`tone()`、`music()`、`update()`。

## 5. 敵はどう追いかけ、密集を避けるのか

### まずプレイヤーへの方向を求める

敵は画面の絵からユニコーンを認識する必要はありません。ゲームは`World.positions`で両者の座標を知っています。

プレイヤーの位置から敵の位置を引きます。

```text
敵:           (100, 100)
ユニコーン:   (400, 500)
差:           (300, 400)
```

右と下に進む方向です。距離は500pxなので差を500で割ると、長さ1の方向`(0.6, 0.8)`になります。これを**正規化**と呼びます。「どちらへ」と「どれだけ速く」を分け、遠いだけで速くなるのを防ぎます。

方向に速度を掛けます。220px/sなら横132px/s、縦176px/sです。説明用に0.1秒なら右13.2px、下17.6px進みます。実際のゲームでは1フレームを最大0.05秒に制限します。

```js
// 曲線と敵同士の間隔調整を省いた直接追跡の例。
const dx = player.x - enemy.x;
const dy = player.y - enemy.y;
const distance = Math.hypot(dx, dy) || 1;
velocity.x = dx / distance * speed;
velocity.y = dy / distance * speed;
```

AISystemが速度を計算し、MovementSystemが位置へ適用します。プレイ中に繰り返すことで移動するプレイヤーを追えます。未来位置を予測せず、現在位置を目指します。

### 敵ごとに少し違う目標を与える

全員が同じ点を目指すと似た経路に集まります。そこでユニコーン周辺に小さく動く目標点を与えます。

```text
目標X = ユニコーンX + cos(角度) × オフセット半径
目標Y = ユニコーンY + sin(角度) × オフセット半径
```

見えない小さな点がユニコーンの周囲を回り、敵がそこを目指すイメージです。IDとプレイ時間で角度を変えます。あくまで目標で、敵を完全な円上に固定するわけではありません。横方向の補正も経路を曲げます。

| 敵 | 移動の特徴 |
|---|---|
| 近距離 | 近い移動目標と、周期的な直接追跡 |
| 遠距離 | 広めの移動目標と横方向の曲線、近づくと発射 |
| 大型 | 移動目標と周期的な直接追跡、緩やかな旋回 |

**120px以内では全種類がユニコーンを直接目標にします。** オフセットと追加曲線はゼロになり、弱い分離力だけ残ります。直接追跡は方向の制御を変えるもので、速度設定を上げるものではありません。

通路を塞ぐ壁がないため、A*のような迷路探索ではなく方向計算を使います。敵弾も発射時のユニコーン位置を狙い、発射後は追尾しません。

### 隣の敵と間隔を空ける

各敵は2つの方向を組み合わせます。

1. プレイヤーへ向かう。
2. 別の敵が近すぎるなら、その敵から離れる。

同じ入口に向かいながら互いに少し空間を空ける人々に似ています。これらの方向を足して移動を決めます。

方向がほぼ打ち消し合った場合、残った小さな方向を最大速度へ増幅せず、小さいまま使います。不安定な動きを防ぐためです。直接追跡中は分離力を弱めて接近できるようにします。

これは**重なりを減らす方法であり、禁止ではありません**。敵同士に硬い壁はなく、衝突円も絵より小さくなっています。全ペア比較ですが最大35体なので扱える規模です。大群では近傍探索を効率化する必要があります。

**実装：** `src/systems/ai-system.ts`の`AISystem.update()`。

## 6. 10ステージはどう構成されるのか

大きなマップを再利用し、小さなデータを変えます。

- プリズム7個の位置。
- 初期の敵数と出現可能な種類。
- 敵と弾の速度ボーナス。
- 増援間隔と最大生存数。
- 空の配色と音楽区間。

序盤は開始点に近いプリズム、後半は広い経路です。遠距離敵はステージ4、大型は7から登場します。ゲートは最初からあり、7色を集めるまで灰色です。

増援は端から**出現可能な種類のうちランダムな1体**を追加します。間隔はステージ1〜2で10秒、3〜5で5秒、6〜8で4秒、9〜10で3秒です。プレイヤーの後ろの集団だけでなく、新しい方向から圧力を生みます。

### 敵が強いだけでは難しくならない

プレイヤーも地図情報、速度、自動雷などを得ます。それらの利点が重なるため、敵の速度だけでは難易度上昇を保証できません。

移動距離、初期数、増援、速度、強化時期が一緒に難易度を決めます。強化の3行は順番に解放され、完走時には9つすべてを得ます。重要なのは**どれを先に取るか**です。

目標は**約5分**です。ローカルダッシュボードで経路と強化順を比較しますが、時間は距離、速度、迂回の仮定による推定です。人の実測クリア時間ではなく、難易度には実際のプレイも必要です。

リトライ時間はステージ記録に入り、強化・敗北画面での待ち時間は入りません。

**実装：** `src/game.ts`の`STAGES`と`ENEMIES`、`src/systems/rules-system.ts`。ダッシュボードは`tools/build-dashboard.mjs`で生成します。

## 7. すべてを小さなZIPに入れる方法

開発用プロジェクトは提出ファイルより大きく、ビルドで必要なものだけ残します。

1. TypeScriptモジュールをJavaScriptにまとめる。
2. 開発専用コードを除き、内部名を短くする。
3. RoadrollerでJavaScriptをさらに小さくパックする。
4. コード、スタイル、WebPデータをindex.htmlひとつに入れる。
5. ZopfliでHTMLを圧縮してZIPにする。

ZIPには**HTMLひとつ**ですが、その中に実際の画像データがあります。画像が手書きの描画コードに変わったわけではありません。

文書、ローカルダッシュボード、元のPNG、宣伝画像は提出物に含まれません。

変更後は実際のZIPを測る必要があります。短いコードが必ず小さく圧縮されるとは限りません。上限近くでは音量値の変更さえ影響します。余裕があれば、そのような変更を受け入れられます。

## 8. 要点

- 認識しやすさが大切な絵は小さな画像、単純な効果はコードで描く。
- 静止画も部分ごとに描く場所を変えれば動いて見える。
- 録音の代わりに小さな音生成器と楽譜を再利用する。
- 敵の圧力は数だけでなく、場所と出現時刻で変わる。
- 絵はゲームサイズで見て、音は聴き、難易度は遊んで確かめる。
- コストを推測せずZIPを測る。

Node検査はデータや時間処理を確認できます。見た目、タッチ操作、音量バランス、難易度には実ブラウザーと試聴も必要です。

コードの構成は[ARCHITECTURE.md](ARCHITECTURE.md)を参照してください。
